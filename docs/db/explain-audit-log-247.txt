audit_log analytics + cleanup: EXPLAIN evidence for issue #247
================================================================================

Environment
-----------
PostgreSQL 16.13 (postgres:16-alpine), default configuration.
Schema built from database/schema.sql.

Seed: 50 api_keys, 2,000,000 audit_log rows spread over 120 days, six
distinct endpoints, a realistic status_code mix (~73% 2xx, the rest
400/429/500), duration_ms 1..400. Table size after seeding: 312 MB.
ANALYZE run before every measurement; VACUUM ANALYZE run after the migration
so the visibility map permits index-only scans.

No query seq-scanned before except Q4's inner scan, which is analysed at the
bottom and is the correct plan for its predicate. The cost being removed here
is heap I/O, not a missing lookup: the 0006 indexes carried only their key
columns, so every matching row had to be visited in the heap to read
status_code / endpoint / duration_ms. The covering indexes make those scans
index-only.

================================================================================
Q4: why the cleanup's Seq Scan is the correct plan
================================================================================

The retention cleanup's inner scan is a Seq Scan both before and after this
migration. That is not a missing index — it is the cheapest plan available,
and forcing an index scan onto it would make it slower.

The predicate is not selective. With a 90-day retention window against 120
days of seeded data:

  older_than_90d |  total
 ----------------+---------
          496072 | 1996000

25% of the table qualifies. The query then takes `LIMIT 1000`, so the
executor needs only the first 1,000 matching rows. A sequential scan reaches
them almost immediately; descending idx_audit_log_ts and then fetching 1,000
scattered ctids would cost more.

The obvious suspicion about this query is its predicate shape — building the
interval by concatenating a bind parameter,
`ts < NOW() - ($1 || ' days')::INTERVAL`, looks like it should defeat the
planner's selectivity estimate. It does not. Measured three ways:

  Q4a  ts < NOW() - ('90' || ' days')::INTERVAL   (current shape)
       Seq Scan, Rows Removed by Filter: 3564, Buffers: hit=32 read=38, 3.899 ms

  Q4b  ts < NOW() - make_interval(days => 90)
       Seq Scan, Rows Removed by Filter: 2992, Buffers: hit=24 read=35, 2.299 ms

  Q4c  ts < (NOW() - INTERVAL '90 days')          (precomputed)
       Seq Scan, Rows Removed by Filter: 2970, Buffers: hit=28 read=31, 1.685 ms

Same plan, same order of cost, in all three. The concatenation is not what
drives the choice; the predicate's low selectivity is. So the cleanup query
is left exactly as it is.

idx_audit_log_ts is nevertheless kept. If the data shape changes — a backlog
cleared down to a small tail, or a longer retention window — the predicate
becomes selective, the planner switches to the index on its own, and it is
there to be used. It is also the only index able to serve a time-range
predicate over rows where api_key_id IS NULL, which idx_audit_log_rollup
excludes by construction.
