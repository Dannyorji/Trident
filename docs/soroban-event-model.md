# Soroban Event Model

This document describes how Trident interprets and decodes Soroban contract events emitted on the Stellar network.

## Event Structure

Every Soroban event exposed by Trident has the following fields:

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Monotonically increasing cursor (`<ledger>-<tx-index>-<event-index>`) |
| `ledger` | number | Ledger sequence in which the event was emitted |
| `timestamp` | string (ISO 8601) | Close time of the containing ledger |
| `contract_id` | string | StrKey-encoded contract address (`C…`) |
| `topics` | array | Decoded XDR topic values (up to 4 `ScVal` entries) |
| `data` | any | Decoded XDR data payload (single `ScVal`) |
| `type` | string | `contract`, `system`, or `diagnostic` |
| `tx_hash` | string | Hash of the transaction that emitted the event |
| `in_successful_tx` | boolean | Whether the containing transaction succeeded |

### topics vs data

Soroban events carry two distinct payloads:

- **topics** — an ordered list of up to four `ScVal` values used for filtering. By convention the first topic is the event name (e.g. `"transfer"`, `"mint"`, `"deposit"`).
- **data** — a single `ScVal` value that holds the event body (amounts, addresses, metadata). This is typically a map or vec for structured payloads.

Trident filters subscriptions against topics only. The data payload is always returned as-decoded.

## XDR-to-JSON Decoding

Trident decodes all `ScVal` types to their natural JSON equivalents:

| ScVal type | JSON representation |
|------------|---------------------|
| `ScvSymbol` | string |
| `ScvString` | string |
| `ScvBool` | boolean |
| `ScvAddress` | string (StrKey: `G…` for accounts, `C…` for contracts) |
| `ScvMap` | object (keys converted to strings) |
| `ScvVec` | array |
| `ScvI128` / `ScvU128` / `ScvI256` / `ScvU256` | **decimal string** (see below) |
| `ScvI64` / `ScvU64` | number |
| `ScvI32` / `ScvU32` | number |
| `ScvBytes` | string (lowercase hex) |
| `ScvTimepoint` / `ScvDuration` | **decimal string** (u64; see below) |
| `ScvVoid` | `null` |
| `ScvError` | string (debug form, e.g. `Contract(ScErrorCode(1))`) |

### Big-integer encoding

128-bit and 256-bit integer types are serialised as **decimal strings** to avoid precision loss in JavaScript (`Number.MAX_SAFE_INTEGER` is only 53 bits). Consumers must parse these with a BigInt library before doing arithmetic.

`ScvTimepoint` and `ScvDuration` are u64-valued and are serialised as decimal
strings for the same reason: a Unix timestamp fits comfortably in 53 bits
today, but the type's full range does not, and a value that silently loses
precision at the top of its range is worse than one that is consistently a
string.

`ScvI64` / `ScvU64` remain JSON numbers for backwards compatibility with
existing consumers. That is a known inconsistency with the rule above — they
have the same 64-bit range problem — and changing it is a breaking change to
the event body, so it is deliberately out of scope here.

`ScvError` is rendered with Rust's debug formatting rather than projected to a
structured object. The variant carries a contract-defined error code whose
meaning is specific to the emitting contract, so there is no stable schema to
promise; the debug form preserves the code without inventing one.

```json
"amount": "1000000000000"
```

### Spec-aware vs positional decoding

When a contract's WASM binary includes a contract spec (generated by the `soroban-sdk` `#[contracttype]` / `#[contractevent]` macros), Trident uses the spec to decode map keys as their named field labels. Without a spec, map entries are decoded positionally with numeric keys (`"0"`, `"1"`, …).

Spec-aware output:
```json
{ "from": "GABC…", "to": "GDEF…", "amount": "5000000" }
```

Positional fallback:
```json
{ "0": "GABC…", "1": "GDEF…", "2": "5000000" }
```

## Worked Examples

### Token transfer (SEP-41 / Stellar Asset Contract)

Emitted by `transfer(from, to, amount)`:

```json
{
  "id": "51234567-1-0",
  "ledger": 51234567,
  "timestamp": "2024-11-01T12:00:00Z",
  "contract_id": "CDLZFC3SYJYDZT7K67VZ75HPJVIEUVNIXF47ZG2FB2RMQQVU2HHGCN",
  "type": "contract",
  "tx_hash": "abc123…",
  "in_successful_tx": true,
  "topics": ["transfer", "GABC…", "GDEF…"],
  "data": {
    "amount": "1000000000"
  }
}
```

### NFT mint

Emitted by a custom NFT contract's `mint(to, token_id)`:

```json
{
  "id": "51234570-0-2",
  "ledger": 51234570,
  "timestamp": "2024-11-01T12:05:00Z",
  "contract_id": "CBNFT…",
  "type": "contract",
  "tx_hash": "def456…",
  "in_successful_tx": true,
  "topics": ["mint"],
  "data": {
    "to": "GABC…",
    "token_id": "42"
  }
}
```

### Custom contract — escrow deposit

Emitted by an escrow contract's `deposit(depositor, amount, release_to)`:

```json
{
  "id": "51234580-2-0",
  "ledger": 51234580,
  "timestamp": "2024-11-01T12:15:00Z",
  "contract_id": "CESCROW…",
  "type": "contract",
  "tx_hash": "ghi789…",
  "in_successful_tx": true,
  "topics": ["deposit"],
  "data": {
    "depositor": "GABC…",
    "release_to": "GDEF…",
    "amount": "500000000"
  }
}
```

## Ordering and Idempotency Guarantees

- Events are delivered in **ledger order**. Within a single ledger, events follow transaction-index then event-index order as defined by the Stellar protocol.
- Each event has a stable `id` cursor of the form `<ledger>-<tx-index>-<event-index>`. Re-subscribing with `cursor=<last-id>` resumes the stream without gaps or duplicates within the retention window.
- The indexer writes events exactly once per ledger; retries are idempotent — duplicate ledger ingestion is a no-op.
- Only events from **successful transactions** (`in_successful_tx: true`) affect on-chain state. Diagnostic events from failed transactions are indexed but are filtered out by default in the streaming API.
